# MSK / Foundations Module Isolation Audit

Audit date: 2026-10-06

## Result

**PASS — module isolation is hardened for the current Foundations + MSK architecture.**

This audit covers the shared attempt/review tables, Smart Review, My Profile, both participation leaderboards, MSK analytics, adaptive quizzes, and the development validation path.

## Database boundary

The shared tables use a non-null `module_key`:

- `question_attempts`
- `quiz_attempts`
- `review_items`
- `review_attempts`

Historical pre-MSK rows were backfilled to `foundations`. New legacy/Foundation writes inherit the `foundations` default unless a caller explicitly supplies another valid module key.

RLS is enabled on all four attempt/review tables. Policies restrict authenticated users to reading/writing their own rows.

The MSK review unique identity is scoped by:

`(user_id, module_key, quiz_id, question_id)`

Attempt-token uniqueness is also module scoped.

## Leaderboards

Migration:

`supabase/migrations/20261006_harden_module_isolation.sql`

The live database functions now use exact module filters:

- Foundations individual/team: `qa.module_key = 'foundations'`
- MSK individual/team: `qa.module_key = 'msk'`

Foundations additionally retains the `quiz_catalog.module = 'Foundations of Medicine'` guard.

This removes reliance on naming conventions or permissive MSK aliases at the leaderboard boundary.

## MSK production writes

`shared/msk-quiz-tracking.js` hard-codes:

`MODULE_KEY = 'msk'`

Every MSK question attempt, quiz attempt, and Smart Review upsert generated by the adapter therefore carries `module_key='msk'`.

The adapter's read/update keys also include the exact MSK module scope.

## MSK reads

The following production surfaces explicitly filter MSK rows:

- `review/msk-review-center.html`
- `review/msk-review-session.html`
- `quiz/msk-adaptive-quiz-builder.html`
- `shared/msk-weakness-radar.js`
- `shared/msk-recommendation-engine.js`
- `shared/msk-adaptive-quiz.js`

The review-session update path is additionally scoped to the signed-in `user_id`.

## My Profile

`my-profile.html` now explicitly scopes attempt/review fetches to the signed-in user in addition to RLS.

Module rendering is partitioned after loading:

- MSK: exact `module_key='msk'` (with legacy metadata recognition only for display compatibility)
- Foundations: exact `module_key='foundations'`; MSK rows are excluded

Quiz History labels rows by module instead of treating every row as Foundations.

## Legacy Foundations review system

The older local-only Foundations review bank uses the separate localStorage namespace:

`fom:review-bank:v1`

It does not import or write the MSK Smart Review tables and does not share the MSK browser namespace.

## Live-data contamination check

A read-only database audit found **0 rows** in `question_attempts`, `quiz_attempts`, or `review_items` that looked MSK-related by quiz ID / metadata while carrying a non-MSK `module_key`.

At the time of this audit, the production database contains only Foundations-scoped attempt/review data because real MSK quizzes have not launched yet.

## End-to-end validation

`admin/msk-e2e-validator.html` runs a synthetic, runtime-only validation through:

Question Bank → Quiz Definition → Tracking → Smart Review → Mastery → Weakness Radar → Recommendation Engine → Adaptive Quiz selection

It deliberately seeds a Foundations row into the same in-memory store and verifies that MSK analytics and adaptive selection do not consume it.

The validator performs no Supabase writes.

## Ongoing rule

Any future module using the shared attempt/review tables must receive its own stable `module_key`. Do not broaden MSK queries to “all non-Foundations” or infer module identity only from quiz names.
